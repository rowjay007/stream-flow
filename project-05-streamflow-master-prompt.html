System Architecture

Stream Topology & Data Flow

StreamFlow's architecture is built around one foundational principle: data moves in one direction, continuously. Producers write to partitioned, Raft-replicated log segments. Stream processors consume, transform, and re-emit. Consumers pull at their own pace. No node ever pushes to another unsolicited — back-pressure is structural, not bolted on.

Stream Data Flow — Producer → Broker → Processor → Sink

Zero-Copy Sendfile: The broker's consumer fetch path uses Linux sendfile(2) to transfer segment data directly from the OS page cache to the consumer socket — without copying bytes into user-space Go memory. This single design decision is responsible for sustaining 10M+ events/sec throughput. Any path that touches []byte in the hot fetch path is a regression.

Consensus Layer

Raft-Based Broker Cluster

StreamFlow implements distributed log replication using the etcd/raft library — not etcd itself, just the pure Raft consensus state machine. Each topic partition has its own Raft group. The leader handles all writes and drives replication to followers. Leader election happens automatically on failure with no Zookeeper, no coordinator service — Raft is the coordinator.

ISR (In-Sync Replicas): A partition's ISR set contains only replicas whose committed offset is within replica.lag.time.max.ms of the leader. A produce request with acks=all blocks until all ISR members have acknowledged. If the ISR shrinks below minISR, the partition becomes read-only — data safety over availability. This is the Kafka model re-implemented in pure Go.

Temporal Processing

Window Types & Watermarks

Windowed aggregations are the fundamental primitive of stream analytics. StreamFlow implements all three standard window types using event-time semantics with watermark-driven progress. The window manager maintains a min-heap priority queue of pending window closes, ordered by watermark threshold.

Window Type 01
Tumbling Window

Fixed-size, non-overlapping windows. Each event belongs to exactly one window. Closed when watermark passes window end. Ideal for periodic aggregations (revenue per minute).

Window Type 02
Sliding Window

Fixed-size, overlapping windows advancing by a slide interval. An event can belong to multiple windows. Used for rolling metrics (P99 latency over last 5 min, updated every 1 min).

Window Type 03
Session Window

Dynamic windows defined by activity gaps. A new session opens on the first event; it closes after an inactivity gap (e.g. 30s of no events). Size varies per user session. Ideal for user behavior analysis.

Watermarks & Late Data: A watermark is the processor's estimate of how far event-time has progressed. StreamFlow uses a heuristic watermark generator: watermark = max_observed_event_time − allowed_lateness. Events arriving after the watermark has passed their window are late. Late events trigger re-computation of the affected window, and a corrected result is re-emitted downstream with a RETRACT flag on the old result and an UPSERT flag on the new one.

Delivery Semantics

Exactly-Once Semantics — The Full Protocol

Exactly-once is the hardest guarantee in distributed systems. StreamFlow implements the full EOS protocol — the same architecture Kafka uses — in pure Go. It requires coordination between three components: the idempotent producer, the transaction coordinator, and the consumer with read-committed isolation.

Go pkg/producer/transactional.go 
// TransactionalProducer provides exactly-once semantics across partitions.
// Usage: Begin → Send(s) → CommitOrAbort. Each step is logged to the
// transaction coordinator before execution — crash at any point is safe.
type TransactionalProducer struct {
    transactionalID string     // unique ID across restarts
    producerID      int64      // assigned by transaction coordinator
    epoch           int16      // bumped on fence — kills zombie producers
    coordinator     TxCoordinator
    sequences       map[TopicPartition]int32 // per-partition sequence numbers
}

// Begin starts a new transaction. Logs AddPartitionsToTxn to coordinator.
func (p *TransactionalProducer) Begin(ctx context.Context) error {
    return p.coordinator.BeginTransaction(ctx, p.transactionalID, p.epoch)
}

// Send appends a record with the current PID + epoch + sequence number.
// Server deduplicates based on (PID, epoch, partition, sequence).
func (p *TransactionalProducer) Send(ctx context.Context, tp TopicPartition, rec Record) error {
    seq := p.sequences[tp]
    batch := RecordBatch{
        ProducerID:  p.producerID,
        Epoch:       p.epoch,
        Sequence:    seq,          // monotonically increasing per partition
        IsTransactional: true,
        Records:     []Record{rec},
    }
    if err := p.coordinator.AppendBatch(ctx, tp, batch); err != nil {
        return fmt.Errorf("send: %w", err)
    }
    p.sequences[tp] = seq + 1
    return nil
}

// Commit writes EndTxn(committed) to the transaction log.
// Consumers with read_committed only see records AFTER this commit marker.
func (p *TransactionalProducer) Commit(ctx context.Context) error {
    return p.coordinator.EndTransaction(ctx, p.transactionalID, p.epoch, Committed)
}
Query Language

StreamSQL — Streaming-Native SQL

StreamSQL is a continuous query language: queries run forever, emitting updated results as new events arrive. It is parsed by an ANTLR4 grammar, compiled to a physical execution graph of Go operator structs, and executed as a pipeline of goroutines connected by buffered channels — one goroutine per operator node.

-- Tumbling window: revenue per merchant per minute SELECT merchant_id, TUMBLE_START(event_time, INTERVAL '1' MINUTE) AS window_start, SUM(amount) AS total_revenue, COUNT(*) AS tx_count FROM payments_stream WHERE status = 'SETTLED' GROUP BY merchant_id, TUMBLE(event_time, INTERVAL '1' MINUTE) EMIT ON WINDOW CLOSE; -- Stream-stream join: enrich payments with fraud score within 5s window SELECT p.payment_id, p.amount, p.merchant_id, f.risk_score, f.decision FROM payments_stream p JOIN fraud_scores_stream f ON p.payment_id = f.payment_id AND f.event_time BETWEEN p.event_time AND p.event_time + INTERVAL '5' SECOND EMIT AFTER MATCHED; -- Session window: user activity per session (30s inactivity gap) SELECT user_id, SESSION_START(event_time, INTERVAL '30' SECOND) AS session_start, SESSION_END(event_time, INTERVAL '30' SECOND) AS session_end, COUNT(DISTINCT page_id) AS pages_viewed FROM clickstream GROUP BY user_id, SESSION(event_time, INTERVAL '30' SECOND) EMIT ON WINDOW CLOSE;
Design Patterns

Core Patterns

  • Event-Driven
    Append-Only Log as Source of Truth

    The distributed log is the system's single source of truth. All state is derived from the log. Any component can rebuild its state by replaying from offset 0. No component stores state that cannot be reconstructed from the log — this is the fundamental correctness guarantee of StreamFlow.

  • CQRS Broker
    Separate Write Path and Read Path

    The broker's produce handler (write path) and fetch handler (read path) share zero data structures. Write path: batch validation → ISR acknowledgment → Raft commit → offset assignment. Read path: offset lookup via mmap index → sendfile segment data → consumer group offset tracking. A bug in one path cannot corrupt the other.

  • Reactive Streams
    Pull-Based Back-Pressure

    Consumers issue fetch requests specifying fetch-max-bytes and fetch-max-wait. The broker responds with up to that many bytes, or blocks for up to fetch-max-wait ms if the log is empty. Consumers control their own throughput. No push, no callback, no overflow. Back-pressure is implicit in the pull protocol.

  • Interpreter
    StreamSQL — Parse → Plan → Execute

    ANTLR4 Listener builds a typed AST from the parse tree. A logical planner converts the AST to a DAG of relational operators (Scan, Filter, Project, Aggregate, Join, Window, Sink). A physical planner applies operator fusion (collapsing Filter+Project into a single pass) and partition affinity (routing to correct broker partition). Execution: one goroutine per operator, connected by buffered channels.

  • Consensus
    Raft Log Replication per Partition

    Each topic partition has its own Raft group of 3 nodes. etcd/raft provides the consensus state machine; StreamFlow implements the storage (log entries are record batches), transport (gRPC), and snapshot (segment file + offset index) interfaces. Leader election is automatic. Split-brain is impossible — Raft requires a quorum (2 of 3) for every commit.

  • Connector SDK
    Source / Sink Plugin Framework

    The connector framework defines two interfaces: Source (Pull records from external system → StreamFlow topic) and Sink (consume StreamFlow topic → push to external system). Built-in connectors implement these for Kafka, PostgreSQL CDC, S3, and HTTP. Third-party connectors implement the same interfaces and are loaded via Go plugin (.so) or as sidecar processes communicating over gRPC.
